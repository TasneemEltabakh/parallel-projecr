Implementation highlights

The hot paths in each of the four Java classes, and the MapReduce primitives doing the heavy lifting.
PowerStats.merge — custom Writable
// associative + commutative merge of two partial aggregates
public void merge(PowerStats other) {
    this.sum   += other.sum;
    this.count += other.count;
    if (other.min < this.min) this.min = other.min;
    if (other.max > this.max) this.max = other.max;
}

public void write(DataOutput o) throws IOException {
    o.writeDouble(sum); o.writeLong(count);
    o.writeDouble(min); o.writeDouble(max);
}
StatsMapper.map — parse + emit singleton
// every line: one double; bucket by line number mod 16
protected void map(LongWritable k, Text v, Context ctx) {
    double x = Double.parseDouble(v.toString().trim());
    int bucket = (int)(lineNo++ & 0xF);   // % 16
    keyOut.set(bucket);
    valOut.set(x, 1L, x, x);                // singleton PowerStats
    ctx.write(keyOut, valOut);
}
StatsReducer.reduce — combiner + reducer
// same class wired as combiner AND reducer
protected void reduce(IntWritable key,
                      Iterable<PowerStats> vals,
                      Context ctx) {
    PowerStats acc = new PowerStats();
    for (PowerStats p : vals) acc.merge(p);
    ctx.write(key, acc);
}
Driver — read K parts, final merge, HDFS write
// after job.waitForCompletion(true)
PowerStats global = new PowerStats();
for (FileStatus fs : fileSystem.listStatus(outDir,
                       p -> p.getName().startsWith("part-r-"))) {
    try (SequenceFile.Reader r = new SequenceFile.Reader(
            conf, SequenceFile.Reader.file(fs.getPath()))) {
        IntWritable k = new IntWritable();
        PowerStats  v = new PowerStats();
        while (r.next(k, v)) global.merge(v);
    }
}
try (FSDataOutputStream out = fileSystem.create(finalPath, true)) {
    out.writeBytes("n=" + global.count + " avg=" + global.avg() +
                   " min=" + global.min + " max=" + global.max + "\n");
}

08

Analysis & findings

What the numbers actually mean, where Hadoop's scaling story breaks down on one node, and the honest cross-stack comparison with Phase 1.
FINDING 01bottleneck

Fixed startup overhead dominates

Each MR job spends seconds requesting containers, launching the application master, JIT-compiling, and tearing down — fixed cost that dwarfs the actual aggregation of ~16 MB of doubles.

  • Wallclock is dominated by framework setup, not compute
  • Analog of Phase 1's memory-bandwidth ceiling: framework cost > work
FINDING 02scaling

Reducer count barely matters on one node

The combiner shrinks shuffle bytes to a few KB. Adding reducers buys almost nothing on a single host because per-reducer container startup dwarfs the per-reducer compute.

  • K = 2, 4, 8 all hover in the same band
  • Real reducer-scaling requires multi-node + much larger data
FINDING 03cross-stack

Hadoop ≠ "faster MPI"

MPI@2 does this aggregate in ~1 ms; Hadoop takes ~20,000 ms per job — roughly 20,000× slower. Hadoop's value isn't single-machine speed; it's horizontal scale-out across many nodes on data that doesn't fit in RAM.

  • Single-node + 16 MB is Hadoop's worst case
  • Right tool, wrong scale — by design, for the assignment
What was measured carefully
  • Warmup pass — the first run is discarded so JVM JIT and HDFS block cache are warm.
  • Wallclock from submit to final HDFS write — same scope Phase 1 measured (compute + reduce, no I/O setup).
  • Blocking barrier — Job.waitForCompletion(true) is synchronous, so the Driver's merge never starts before all reducers finish.
  • Best of 15 runs reported as the headline; container scheduling jitter is the dominant noise source.
Where does the 19 seconds go? — and how to make it faster

Each MR job spends >99% of its wallclock inside Hadoop's framework, not on the 16 MB of arithmetic. Approximate breakdown of a single --reduces 1 run:

StageTimeWhat
hadoop jar client JVM~2 sCold-load Hadoop client, connect to ResourceManager
AM container scheduling + JVM~4 sRM picks a node, NodeManager launches the MapReduce AppMaster
Map container negotiation + JVMs~6 sRM heartbeat poll, NM launches map JVMs (one per split)
Shuffle + sort~1 sDisk write/read even though combiner cut payload to KB
Reduce container + JVM~4 sSame negotiation pattern as maps
AM cleanup + output commit~2 sFinal HDFS commit, AM teardown
Actual compute on 16 MB~0.1 sWhat the job nominally does

We measured three modes empirically on this hardware (5 reps each, best time, --reduces 1):

ModeBest (ms)vs defaultWhat it skips
Default MR + YARN19,3361.00×Nothing — full cluster path
Uber mode -Dmapreduce.job.ubertask.enable=true11,3121.71×Map/reduce containers — AM runs the whole job in-process
LocalJobRunner -Dmapreduce.framework.name=local3,5585.43×YARN entirely — whole MR runs in the client JVM, no AM, no containers. Still reads from HDFS.
Phase 1 sequential C (for scale)3.186,080×Hadoop entirely. Native compiled code, no JVM.
Phase 1 MPI @ 2 (for scale)0.60931,750×As above + shared-memory parallelism.

The interesting observation: LocalJobRunner runs the same Mapper/Reducer/Driver code as the YARN path. The 5.4× speedup is pure overhead removal — no algorithmic change. The remaining ~3.5 s is JVM cold-start (~1 s) + Hadoop framework class loading (~1.5 s) + actual MR step in-process (~1 s including the HDFS read/write). The "slowness" of Hadoop on tiny data is the cluster, not MapReduce.

Two practical takeaways:

  • Unit-test your MR jobs against LocalJobRunner — you get the same correctness signal in ~3 s instead of 20 s per iteration.
  • Don't reach for full YARN until the per-job compute is large enough that the ~15 s of overhead becomes a small percentage of the total — rule of thumb, minutes-scale jobs on hundreds-of-GB inputs.
The honest take This is a single-node pseudo-distributed cluster — not a fair throughput test for what Hadoop is actually built for. The reducer sweep flattens (and inverts) because per-reducer container startup eats the per-reducer work, and the whole job is gated by framework overhead on a tiny ~12 MB input. The point of this phase isn't to beat MPI — it's to demonstrate the MapReduce primitives correctly and to understand why a framework designed for petabytes on thousands of nodes looks slow when handed a 16 MB job on one laptop.

Reproducing the run

From a clean Linux/macOS host with Docker and a JDK installed, to a populated results.csv and a HDFS-resident final result.
Step 01 · Bring up the Hadoop cluster
# Docker (Fedora shown — adapt for your distro)
sudo dnf install docker
sudo systemctl enable --now docker

# JDK with --release 8 support
sudo dnf install java-latest-openjdk-devel

# spin up apache/hadoop:3 pseudo-distributed
./docker/run-cluster.sh
# waits until HDFS + YARN are ready inside the container

# one-time: copy Hadoop client jars to host for javac
./docker/extract-hadoop-jars.sh
Step 02 · Build, upload, run, bench
# build phase2-mr.jar (host javac, Java 8 bytecode)
make

# upload data.txt into HDFS — one time per session
make put

# single end-to-end run at --reduces 4
make test

# full sweep: 15 runs × 4 reducer counts → results.csv
make bench

# read the final HDFS result
docker exec -u hadoop hadoop-pseudo \
  hdfs dfs -cat /output/final/stats.txt
