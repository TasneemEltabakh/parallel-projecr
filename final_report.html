Same problem, three implementations. What did each tool buy us?

Compute average / minimum / maximum of a numeric column over a 2 million-row dataset, three ways: a sequential C baseline, an MPI parallel version, and a Hadoop MapReduce job. The point isn't winning a benchmark — it's understanding what each tool is for, and what its overhead actually costs you.

03Phase 1 — Sequential C vs MPI

Both binaries do the same work in a single pass over a[N]. The MPI version distributes the array with MPI_Scatterv and combines partial results with MPI_Reduce.

What we learned Scaling is flat from n=2 to n=8. The workload is memory-bandwidth-bound — the loop does ~2 instructions per element but one DRAM read. The 16 MB array doesn't fit in L3, so adding ranks on the same memory bus can't buy more bandwidth. Textbook linear speedup would need either a multi-node cluster or per-element compute (e.g. sin(v)·cos(v)).

04Phase 2 — Hadoop MapReduce

Same operation, packaged as a single Java MR job. Apache Hadoop 3.3.6 runs pseudo-distributed in a Docker container; we vary --reduces over 1/2/4/8 as the analog to MPI's process-count sweep.

flowchart LR A[hdfs:///input/data.txt] --> M[StatsMapper
bucket = lineNo mod 16] M --> C[StatsReducer
as combiner] C -->|shuffle| R[StatsReducer
K reducers] R --> P[K · part-r-* SequenceFiles] P --> D[Driver
client-side merge] D --> O[hdfs:///output/final/stats.txt] style M fill:#eef2f7,stroke:#1e3a5f style R fill:#eef2f7,stroke:#1e3a5f style O fill:#e7efe9,stroke:#15613e

Why bucket by lineNo % 16? A single key would route all data to one reducer regardless of --reduces N — the sweep would be meaningless. 16 buckets > the largest K in the sweep, so 1/2/4/8 reducers all get real load.

Unexpected but explainable More reducers → slower. On a single-node cluster, every extra reducer adds container-launch overhead while the per-reducer compute stays trivial (combiner already shrunk the shuffle to ~KB). This isn't a bug; it's pseudo-distributed Hadoop honestly reporting its overhead.

Where do the ~19 seconds go?

Each MR job spends >99% of its wallclock in framework overhead, not on the 16 MB of arithmetic. Approximate breakdown of one --reduces 1 run:

StageTimeWhat
hadoop jar startup~2 sCold-load Hadoop client, connect to ResourceManager
AM scheduling + JVM~4 sRM picks node, NM launches AppMaster
Map containers + JVMs~6 sHeartbeat-driven, one JVM per split
Shuffle + sort~1 sDisk I/O even with KB-sized payload
Reduce containers + JVMs~4 sSame pattern as maps
AM cleanup + commit~2 sFinal HDFS commit, AM teardown
Actual compute on 16 MB~0.1 sWhat the job nominally does

Speed ladder — strip overhead, watch it fall

We empirically measured three modes, all running the same Mapper/Reducer/Driver code on the same HDFS input:

Modebest (ms)vs defaultWhat it skips
Default MR + YARN19,3361.00×Nothing — full cluster path
Uber mode -Dmapreduce.job.ubertask.enable=true11,3121.71×Map/reduce containers — AM runs the whole job in-process
LocalJobRunner -Dmapreduce.framework.name=local3,5585.43×YARN entirely — runs in the client JVM, still reads from HDFS

LocalJobRunner's remaining ~3.5 s is JVM cold-start (~1 s) + Hadoop framework class loading (~1.5 s) + in-process MR (~1 s). The "slowness" of Hadoop on tiny data is the cluster machinery, not MapReduce itself.

Right tool for the job On 16 MB of data on one laptop, sequential C wins. MPI is 5× faster than sequential but capped by memory bandwidth. Hadoop's ~20 second per-job overhead is fixed regardless of input size — it only pays off when per-job compute is also seconds-or-minutes long, which means hundreds-of-GB inputs across many nodes.

06Key takeaways

What this project demonstrates
  • All three implementations are correct — bit-exact min/max, mean within 1e-9 of NumPy, across 7 distinct configurations.
  • MPI scales to a hardware ceiling, not a code ceiling. Phase 1's flat scaling at n≥2 is a memory bandwidth story, documented honestly rather than hidden.
  • Hadoop's overhead is the headline. 99% of wallclock is framework, 1% is work. Quantifying it via uber-mode and LocalJobRunner makes the cost concrete instead of hand-waved.
  • Cross-stack comparison is the point. Same problem · same data · same correctness · 31,750× difference in wallclock. Each tool is correct for a different scale of problem.
When to reach for which
Data fits on one machine, you control the code Sequential C / OpenMP. If it's bandwidth-bound, accept the ceiling.
Data fits but you want shared-memory parallelism MPI on one node, or threads. Watch for the bandwidth wall.
Data doesn't fit on one machine and the per-job compute is minutes+ Hadoop / Spark on a real cluster. Overhead amortizes.
Testing the logic of an MR job locally mapreduce.framework.name=local. ~3 s instead of ~20 s per iteration.
