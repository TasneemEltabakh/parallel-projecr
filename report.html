Implementation highlights

The hot path on each side, plus the MPI primitives doing the heavy lifting.
Sequential — timed inner loop
// warm-up so timing measures steady-state DRAM
for (size_t i = 0; i < n; i++) warm += a[i];

double t0 = now_ms();
double sum = 0.0, mx = -DBL_MAX, mn = DBL_MAX;
for (size_t i = 0; i < n; i++) {
    double v = a[i];
    sum += v;
    if (v > mx) mx = v;
    if (v < mn) mn = v;
}
double t1 = now_ms();
double avg = sum / (double)n;
MPI — scatter, local work, reduce
MPI_Bcast(&N, 1, MPI_LONG_LONG, 0, MPI_COMM_WORLD);

// Scatterv handles N % np ≠ 0
MPI_Scatterv(full, cnts, disp, MPI_DOUBLE,
             buf,  my_n,       MPI_DOUBLE,
             0, MPI_COMM_WORLD);

MPI_Barrier(MPI_COMM_WORLD);
double t0 = MPI_Wtime();
// local sum / mx / mn over buf[my_n]

MPI_Reduce(&s,  &gsum, 1, MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);
MPI_Reduce(&mx, &gmx,  1, MPI_DOUBLE, MPI_MAX, 0, MPI_COMM_WORLD);
MPI_Reduce(&mn, &gmn,  1, MPI_DOUBLE, MPI_MIN, 0, MPI_COMM_WORLD);
01 · Broadcast
MPI_Bcast
Send the array length N from rank 0 to every other rank.
02 · Split
MPI_Scatterv
Distribute the array as per-rank chunks; handles uneven divisions.
03 · Combine
MPI_Reduce × 3
Aggregate the partial results — SUM, MAX, MIN — at rank 0.
04 · Measure
MPI_Wtime
Barrier-bounded high-resolution clock around the compute region.

08

Analysis & findings

What the numbers actually mean, where scaling breaks, and the one anomaly worth being honest about.
FINDING 01bottleneck

Memory-bandwidth-bound

Each element costs roughly two instructions but one DRAM read. At 16 MB > L3, the loop is gated by memory bandwidth — not by arithmetic.

  • Back-to-back passes are equally slow — no L3 reuse
  • More cores can't help once the bus is full
FINDING 02scaling

Flat scaling from 2 → 8

Median time at n = 2, 4 and 8 hovers around 1.2 ms — within noise of each other. More ranks on the same memory bus don't buy more bandwidth.

  • n = 8 is marginally worse — overhead grows
  • Best at n = 2 (0.61 ms) is a fortunate scheduling sample
FINDING 03anomaly

The n = 1 measurement

MPI at n = 1 is 3× faster than sequential — but it is still one process. SIMD, loop type, cache, frequency, alignment and timing API were all ruled out.

  • Only reproduces via benchmark.ps1
  • Likely: hybrid-CPU P/E-core scheduling of mpiexec children
What was measured carefully
  • Warmup pass in both binaries — the timed region measures steady state, not first-touch.
  • Disk I/O excluded — fread happens before the timed region in both implementations.
  • Barrier before the timer in MPI — no rank gets a head start.
  • Best of 15 runs reported as the headline; Windows scheduling jitter is the main noise source.
The honest take The workload is memory-bandwidth-bound on a single machine, so MPI scaling tops out near the bandwidth ceiling. A textbook linear curve would require either a multi-node cluster, or replacing the trivial reduction with per-element compute (for example sin(v)·cos(v)). We kept the honest numbers because they show real engineering judgment about where the bottleneck actually lives.

Reproducing the run

From a clean Windows machine to a populated results.csv in under five minutes.
Step 01 · One-time toolchain setup
# Microsoft MPI runtime + SDK
winget install Microsoft.msmpi
winget install Microsoft.msmpisdk

# gcc via MSYS2
winget install MSYS2.MSYS2
pacman -S mingw-w64-x86_64-gcc

# Python deps for prep script
pip install pandas numpy
Step 02 · Run the pipeline
python data\prep.py
# download + write data.bin (~30s)

.\src\build.ps1
# compile both .exe into bin\

.\bin\sequential.exe .\data\data.bin
mpiexec -n 4 .\bin\parallel_mpi.exe .\data\data.bin

.\bench\benchmark.ps1
# full sweep, writes results.csv
